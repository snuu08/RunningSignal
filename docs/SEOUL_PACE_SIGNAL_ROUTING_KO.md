# 서울 페이스·신호 도착 시각 기반 러닝 경로

최신 배포·휴대폰 실측 절차: [2026-10-15 배포 준비 기록](SEOUL_RELEASE_20261015_KO.md).

## 목적

서울의 실제 출발 위치에서 보행 경로 후보를 만들고, 러너의 페이스와 출발 시각으로 각 횡단보도 도착 시각을 계산한다. 보행신호의 진입 가능 시간과 횡단 시간을 반영해 이동·대기 합계가 짧은 경로를 추천한다. 허용 우회 거리와 방향 전환 제한은 유지한다.

## 구현한 동작

1. TMAP 보행 후보의 거리와 페이스로 도착 시각을 계산한다. 앞 횡단보도의 대기와 실제 횡단 시간이 뒤 횡단보도 도착 시각에 누적된다.
2. 추천 화면에서 후보별 거리·예상 시간·신호 대기·정지 횟수를 비교한다. `지금 출발하면 좋은 경로 다시 비교`는 현재 시각으로 재평가한다. 준비 화면 진입 전에도 신호를 다시 계산한다.
3. GPS 시작 후 선택 경로의 남은 신호를 즉시 재평가하고, 러닝 중 20초마다 갱신한다. 일시정지 동안 요청을 멈추고 재개 시 현재 시각으로 계산한다. 지나간 신호의 대기를 다시 더하지 않는다. 횡단 중이면 출구까지 걷는 시간을 다음 ETA에 반영한다.
4. 최근 30초 GPS 이동 페이스를 우선 사용하고, 측정이 부족하면 60초 페이스 또는 입력 페이스를 사용한다. 정확도 30m를 초과하는 위치·수신 공백·일시정지·GPS 불확실성보다 작은 흔들림은 실측 페이스에서 제외한다. 정지 대기시간을 다음 러닝 구간 페이스에 더하지 않는다.
5. `현재 페이스로 경로 다시 찾기`는 실제 GPS 좌표와 실측 페이스를 사용한다. API의 추천·신호 결과를 유지한다. 왕복의 원래 도착점을 유지하고 이미 지난 경유지는 다시 요청하지 않는다.
6. 다음 녹색 진입 구간에 맞출 수 있는 경우만 구체적인 느린 페이스를 제안한다. 현재보다 최대 15% 느린 페이스만 검토하며, 횡단보도 30m 이내에서는 페이스 변경을 제안하지 않는다. 점멸 시작 이후 새 진입은 예측하지 않는다.

TMAP 총거리와 지도 선의 길이가 다르면 횡단보도·현재 위치를 총거리 단위로 비례 변환한다. GPS 기록 거리는 별도로 계산하며 지도 선에 강제로 붙이지 않는다.

## 서울 실시간 어댑터

공식 문서 확인일: 2026-10-11.

- [실시간 신호정보 및 잔여시간 현시 API, data_id=10381](https://t-data.seoul.go.kr/dataprovide/trafficdataviewopenapi.do?data_id=10381)
- [신규 실시간 API 안내, 2026-09-17](https://t-data.seoul.go.kr/board/notice/detail.do?boardId=102)
- 게이트웨이: `https://t-data.seoul.go.kr/apig/apiman-gateway/tapi/v2xSignalPhaseTimingFusionCurrentInfo/1.0`
- 필수 요청: 소문자 `apikey`, `itstId`. 이전 API의 `apiKey`와 구분한다.
- 보행 상태: 방향별 `*PdsgStatNm`. 보행 잔여값: `*PdsgRmdrCs`. 차량 직진 상태를 보행신호로 사용하지 않는다.

공식 표의 필드명은 센티초, 값 설명은 1/10초로 서로 다르다. 진단 화면은 원본값을 유지한다. 실제 횡단 방향과 잔여값 단위를 확인한 `liveMappings`만 예측에 쓴다.

`server/seoul-live-provider.ts`는 이미 검증된 고정 주기의 현재 현시와 실제 보행 상태·잔여값이 일치하는지 확인한다. 현재 상태 한 번으로 주기·녹색 지속시간·epoch를 만들어내지 않는다. 확인 시각은 HTTP 요청 시각이 아닌 원천 `trsmUtcTime`이다. 원천 시각 10초 초과 지연, 다른 교차로, 단위 미확인, 상태 불일치, 감응식 운영은 확인 실패로 처리한다. 후보 여러 개가 같은 교차로를 지나면 평가 요청 안에서 API 호출을 공유한다.

## 실제 연결에 필요한 데이터

현재 저장소의 정적 pilot 자료나 자동 테스트를 서울 현장 검증으로 간주하지 않는다. 기본 공개 예측 설정은 `false`다.

2026-10-11 실제 배포 서버 `https://snuu08-runningsignal.netlify.app`를 호출했다. `/api/status`는 서울 키가 설정됐다고 반환했지만, 이는 인증 성공이나 신호 수신 증거가 아니다. 배포된 `/api/signals/seoul?service=current&itstId=2207`는 최신 서비스 미지원으로 HTTP 400을 반환했다. 기존 `phase`와 `timing`은 각각 약 19초 뒤 HTTP 502와 제공기관 연결 실패를 반환했다. 따라서 실제 신호 수신·승인 범위·잔여값 단위는 아직 확인되지 않았다. 최신 어댑터가 포함된 배포에서 다시 호출해야 한다. 키 값을 로그·소스·클라이언트에 노출하지 않았다.

운영 환경에는 기존 서버 변수 `TMAP_APP_KEY`, `KAKAO_REST_API_KEY`, `SEOUL_TDATA_API_KEY`를 설정한다. 키는 브라우저 변수나 소스 파일에 넣지 않는다.

verified bundle에는 해당 서울 구간의 실제 자료가 필요하다.

- `crossings`: 횡단 양끝점, 러닝 진행 방향, 교차로 ID, 보행신호 그룹, 횡단 길이와 근거.
- `plans`: 실제 고정 주기·epoch·진입 구간·점멸·종료 시각, 적용 요일·시간대와 검증 근거.
- `surveys`: 후보의 전체 보행 경로를 조사한 coverage와 모든 횡단 ID.
- `liveMappings`: 각 횡단과 실제 T-DATA 보행 방향 필드·단위의 대응.

`liveMappings` 항목의 필드는 다음과 같다. 현장 또는 신뢰할 수 있는 원천으로 확인한 값만 넣는다.

| 필드 | 값 |
| --- | --- |
| `crossingInternalId` | verified 횡단의 정확한 내부 ID |
| `direction` | `nt`, `et`, `st`, `wt`, `ne`, `se`, `sw`, `nw` 중 확인된 보행 필드 |
| `remainingUnit` | 실측 확인한 `deciseconds` 또는 `centiseconds` |
| `redEndsAtEntryStart` | 적색 잔여값이 다음 보행 녹색 시작까지임을 확인한 경우만 `true` |
| `verifiedAtMs` | 방향·단위를 확인한 시각, epoch ms |
| `evidence` | 확인 방법·원천·관측 근거 |

`SIGNAL_VERIFIED_PATH` 또는 `SIGNAL_VERIFIED_JSON`으로 자료를 전달하고 해당 교차로만 `SIGNAL_PREDICTION_SCOPES`에 등록한다. 실제 매핑·운영계획·coverage를 검증한 뒤 해당 배포 환경에서 공개 예측을 켠다. 서울 전체를 조사 없이 일괄 활성화하지 않는다.

현재 응답 수집 명령은 서버 키를 설정한 환경에서 실행한다.

```bash
npm run signals -- collect --provider tdata --service current --itstId <실제_교차로_ID>
```

키와 HTTP 응답 수신시각만으로는 미래 도착 시 대기를 계산할 수 없다. 자료가 부족한 경로는 `신호 대기 미확인`을 표시하고 실제 보행 경로는 계속 제공한다.

## 검증 범위

자동 테스트는 서울 좌표의 모의 이동과 모의 신호 응답이다. 6:00/km와 5:00/km에서 추천 경로가 바뀌는 경우, 누적 대기, 이미 지난 횡단, GPS 정지 흔들림, 신호 갱신·일시정지·오류, 현재 신호와 문서 계획 일치 여부를 검사한다. 실제 전화기의 서울 야외 GPS, 잠금 화면, 제공기관 라이브 응답, 현장 신호 대기 오차 검증은 남아 있다.

## API

`POST /api/routes/evaluate`는 경로 후보 1~5개, `pace`, 후보별 `traveledM`을 받아 현재 시각의 신호 예측을 반환한다. TMAP 경로를 다시 요청하지 않는다. 클라이언트가 넣은 신호 계획은 읽지 않고 서버 자료만 사용한다. 좌표·거리·진행 위치·요청 크기를 제한한다.
