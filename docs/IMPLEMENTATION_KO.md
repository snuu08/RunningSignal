# FLOW RUN — 실제 서비스 구현 명세와 인수 안내

이 문서는 사용자와의 대화 및 저장소의 기존 화면을 기준으로 작성했다. 기존 `src/features`, `src/providers/mock` 체험 모드는 보존하고, 실제 좌표·실제 GPS·실제 계정을 사용하는 경로를 `src/real`에 추가했다.

**이 변경안은 실제 API와 연결할 수 있는 베타 구현이다. 신호를 놓치지 않는 경로를 보장하는 완성 서비스나 앱스토어 출시 완료본이 아니다.** 이번 작업에서 실제 사용자 키로 외부 제공기관을 호출하지 않았고, 제공기관의 승인 범위·응답·요금제·야외 GPS·계정 메일 발송은 검증되지 않았다.

## 1. 실행과 모드 구분

```bash
npm ci
cp .env.example .env.local
npm run dev
```

`.env.local`의 빈 값을 관리 화면에서 가져온 현재 유효한 값으로 채운다. 대화에 붙였던 잘리거나 노출된 키를 복원·추측하지 않는다. 환경변수를 변경하면 개발 서버를 재시작한다.

- `VITE_APP_MODE=real`: 실제 모드. `/real/home`에서 시작한다. 환경변수가 없어도 `/real/home`으로 실제 모드를 확인할 수 있다.
- 기본값 `demo`: 기존 가상 보행망·가상 계정·시뮬레이션 유지. 실제 GPS 기록과 저장소를 공유하지 않는다.
- 실제 모드의 지도·장소·경로 키가 없으면 각 기능에 연결 필요 메시지를 표시한다. 경로 없이 GPS 러닝과 기기 저장은 계속 가능하다.
- `npm run preview`는 정적 산출물 확인용이며 API 서버를 실행하지 않는다. API 개발 확인은 `npm run dev`, 배포 확인은 Netlify Functions 환경에서 한다.
- Netlify 환경변수에서 `VITE_` 값은 빌드 시점에 필요하고 나머지 키는 Functions 실행 환경에도 설정해야 한다.
- Supabase의 URL Configuration에 실제 서비스 URL과 `/real/auth` 리다이렉트 URL을 등록한다.

## 2. 준비한 API별 상태와 연결 위치

| 준비한 항목 | 앱에서 맡는 역할 | 이번 구현 | 별도 확인할 내용 |
|---|---|---|---|
| MapLibre GL JS | 지도 조작·선·위치 마커 렌더링 | 설치, `RealMap.tsx` 연결 | 데이터 제공 API가 아니라 렌더링 라이브러리 |
| MapTiler | 검은 배경 실제 지도 | `VITE_MAPTILER_KEY`, `VITE_MAPTILER_STYLE` 연결 | 허용 Origin, 요금, 지도 스타일 ID, 출처 표시 |
| MapTiler Static Maps | 기록 카드의 정적 지도 이미지 | 현재는 실제 경로 모양 SVG 사용 | 별도 Static API 호출은 미구현. 정적 배경지도가 꼭 필요할 때 추가 |
| 카카오 JavaScript 키 | 카카오 JS SDK 인증 | 이 구조에서는 사용하지 않음 | MapLibre 지도에 카카오 JS SDK를 중복 설치할 필요 없음 |
| 카카오 Local REST | 출발지·목적지·경유지 장소 검색 | 서버 `KAKAO_REST_API_KEY`, `/api/places` | **JavaScript 키와 다른 REST 키 필요.** 현재 키워드 검색 구현, 주소 전용 검색·역지오코딩은 추가 가능 |
| TMAP 보행자 경로 | 실제 보행 가능 경로 좌표와 거리 | 서버 `TMAP_APP_KEY`, `/api/routes` | 보행자 API 승인, 한도, 다른 지도와 결과 결합·저장 이용조건 확인 |
| 서울 신호제어기 신호 정보 | 교차로의 현재 방향별 신호 상태 | `SEOUL_TDATA_API_KEY`, `service=phase` 프록시 | 보행 필드와 차량 필드 분리, 수집시각·지연 검증 |
| 서울 신호제어기 잔여시간 | 현재 상태가 끝날 때까지 남은 값 | `service=timing` 프록시 | 단위·타임스탬프 확인. 현재 잔여값으로 여러 주기 뒤를 단정하지 않음 |
| 서울 교차로 MAP | 교차로 ID·위치·기반 정보 | 카탈로그상 **파일**(data_id=10144). `service=crossroad`는 게이트웨이를 호출하지 않고 503 | 교차로 중심은 횡단 시작점이 아님. Open API 경로를 추측하지 않음 |
| 서울 신호 연결 MAP | 신호와 방향/연결 관계 | `service=connection` 프록시 | 보행 방향과 실제 횡단 구간의 대응 여부 확인 |
| 서울 차로 MAP | 차로 형상·구성 | `service=lane` 프록시 | 차량 차로를 러닝 경로로 사용하지 않음 |
| UTIC 교차로 기반 정보 | 교차로·방향·현시 매핑 | `CrossRoadInfoService/download` 파일 계약. JSON 프록시 없음 | xlsx는 CLI 자리. XY는 WGS84 범위만. 횡단 양끝점 아님 |
| UTIC 운영계획 | 주기·옵셋·현시 값 | `/api/signals/utic?op=getPlanCROPInfo&srchCTId=L01` | 주기·링 분할 파싱. epoch·보행 창은 만들지 않음. `engineReady=false` |
| UTIC 평일·특수일·예약 계획 | 날짜·시간대에 적용되는 계획 선택 | `getPlanCRWDInfo` / `CRHD` / `CRRS` 파서·선택기 | 예약 점멸·감응은 FixedPlan 아님. L01 코드 ≠ 서울 데이터 존재 |
| UTIC SIGNALMAP/보행맵 | 보행 신호 구성과 횡단 대응 | `op=getSigMapCRInfo` | PED1–8 원문 보관. 녹색 창으로 매핑하지 않음 |
| 경찰청 교차로 기반정보 문서 | 해당 공공데이터 서비스의 교차로 기반정보 | 문서 원본·정확한 서비스 명세 수령 대기 | `.docx` 파일명과 인증키만으로 엔드포인트를 추측하지 않음 |
| 행안부/한국지역정보개발원 실시간 신호등 | 해당 데이터셋의 상태·위치 정보 | 베이스 `https://apis.data.go.kr/B551982/rti` | 오퍼레이션 경로 없음. 추측 호출 안 함. 현재 상태 ≠ 운영계획 |
| 전국신호등표준데이터 XLS | 신호등 시설 위치 목록 | CSV ETL·placeholder 매핑 (`data/signals`). XLS 바이너리는 열지 않음 | 정적 시설 정보이며 주기·녹색을 만들지 않음 |
| 서울 횡단보도 시설물 | 횡단보도 위치·부착대 등 | GeoJSON ETL 자리. 데이터셋 ID·컬럼 사전 미확인 | 중심·부착대·실제 횡단 양끝점 구분. 컬럼명 추측 매핑 확정 금지 |
| 서울 자치구별 도보 네트워크 | 보행 링크·노드 | TMAP 경로 + `LINK_CODE` 코드표 | 보행 비트 파싱. 계단·육교 코드와 공간 파일은 별도 |
| 기기 위치 API | GPS 좌표·정확도·시간 | `navigator.geolocation` 연결 | 별도 발급키 없음. HTTPS·권한·기기 검증 필요 |
| 회원 계정/DB/메일 | 실제 가입·로그인·메일·기록 동기화 | Supabase 연결 코드·SQL 추가 | 사용자가 준비한 목록에 없던 항목. 새 프로젝트 설정·메일 발송 검증 필요 |

서울 신호 프록시의 내부 요청 예:

```text
GET /api/signals/seoul?itstId=검증할교차로ID&service=phase
GET /api/signals/seoul?itstId=검증할교차로ID&service=timing
GET /api/signals/seoul?itstId=검증할교차로ID&service=connection
GET /api/signals/seoul?itstId=검증할교차로ID&service=lane
GET /api/signals/utic?op=getPlanCROPInfo&srchCTId=L01
GET /api/signals/utic?op=getPlanCRWDInfo&srchCTId=L01
GET /api/signals/utic?op=getSigMapCRInfo&srchCTId=L01
# op=crossInfo 는 파일. 프록시는 503.
```

서버에서만 제공기관에 `apiKey`를 붙인다. 공식 문서의 파라미터 대소문자를 사용한다. HTTPS 연결 실패 시 HTTP로 몰래 전환하지 않는다. 응답이 왔다는 사실과 미래 예측에 쓸 수 있다는 사실을 별도로 관리한다.

## 3. 화면·버튼별 동작

표의 ‘구현’은 코드 연결을 의미한다. 외부 서버의 운영 검증까지 완료됐다는 뜻이 아니다.

### 진입·계정·첫 설정

| 화면/조작 | 눌렀을 때 실제 동작 | 입력·예외 처리 | 상태 |
|---|---|---|---|
| 시작 로고 | 기존 러너 SVG의 1.8초 확대/축소 | reduced-motion 존중 | 실제 인증·로딩 화면에 적용. 기존 전용 스플래시는 데모 보존 |
| 로그인 | Supabase 이메일/비밀번호 인증 | 실제 서버 미설정이면 비활성 | 구현 |
| 회원가입 | 이메일 인증 가입 요청 | 이메일, 8자 이상 비밀번호, 정책 동의 | 구현. 운영용 정책 게시·SMTP 검증 필요 |
| 비밀번호 찾기 | 재설정 메일 요청 | 가입 여부를 확정 노출하지 않는 문구 | 구현 |
| 새 비밀번호 저장 | 복구 세션으로 비밀번호 갱신 | 복구 링크 만료는 제공기관 오류 처리 | 구현. 실제 메일 E2E 필요 |
| 로그인 상태 유지 | Supabase 세션 유지/토큰 갱신 | 게스트 기록과 계정 기록 저장 공간 분리 | 기본 유지. 별도 ‘유지 안 함’ 선택은 추가 필요 |
| 계정 없이 기기에 기록 | 서버 계정을 만들지 않고 GPS/로컬 기능 시작 | 로그인한 척하는 가상 계정 생성 없음 | 구현 |
| 지역 선택 | 서울·인천·대구·성남 분류 저장 | 선택 가능과 신호 예측 지원을 동일시하지 않음 | 구현 |
| 닉네임·평균 페이스 저장 | 기기 프로필, 로그인 시 계정 동기화 | 닉네임 2~20자, 페이스 120~1800초/km | 구현 |
| 설정에서 지역·닉네임 수정 | 프로필 갱신 | 저장 실패 시 안내, 이전 운동 기록은 유지 | 구현 |

### 경로 계산·추천

| 조작 | 실제 동작 | 예외/정확성 규칙 | 상태 |
|---|---|---|---|
| 로딩 | 최소 1초, 실제 요청 완료까지 표시 | 신호 미검증인데 ‘신호 분석 완료’로 표시하지 않음 | 구현 |
| 로딩 취소 | AbortController로 응답 적용 취소 | 늦게 도착한 이전 후보가 새 화면을 덮지 않음 | 구현 |
| 경로 지도 | 현재 후보 1개를 전체 범위로 표시 | WGS84 경로 좌표 사용 | 구현 |
| 거리·예상 시간 | 제공 거리 × 사용자 페이스 | 신호 미검증 시 ‘대기 제외 예상’ | 구현 |
| 신호 수·대기·예상 정지 | 검증된 횡단 연결/계획이 있을 때만 계산 | 자료 없음 ≠ 0개/0초 | 엔진 구현, 실제 화면 예측 비활성 |
| 아니요, 다른 루트 | 필터를 통과한 다음 고유 후보 | 후보가 없으면 알림. 아무 골목으로 무제한 우회하지 않음 | 구현 |
| 조건 수정 | 홈 입력으로 복귀 | 원래 출발지·목적지·경유지 유지 | 구현 |
| 예, 이 루트로 | 시작 준비 화면으로 이동 | 아직 운동 기록 시작 아님 | 구현 |

## 4. 경로 계산의 정확한 규칙

### 실제 보행 후보

1. 서버가 출발·목적·경유 WGS84 좌표와 `pace`(초/km)를 검증한다.
2. TMAP에 `4`(대로우선), `30`(최단거리+계단제외), `0`(추천) 옵션을 요청한다. 한 번의 루트 찾기는 최대 3회 제공기관 호출이다.
3. `passList`에 사용자가 선택한 경유지를 전달한다. 왕복은 반환점을 경유지로 두고 종점을 출발지로 지정한다.
4. 거리에는 TMAP `totalDistance`를 사용한다. TMAP `totalTime`을 사용자의 러닝 시간으로 표시하지 않는다.
5. 30m 간격으로 경로를 샘플링해 50도 이상 급격한 방향 전환과 약 90m 이내 좌우 반복을 계산한다. 이 값은 초기 휴리스틱이며 골목/안전 여부의 확정 판정이 아니다.
6. 가장 짧은 후보를 기준으로 `추가거리 <= min(기준거리 × 허용비율, 최대추가거리)`를 적용한다.
7. 중복 경로를 제거하고 지그재그·급격한 회전·거리를 순서대로 비교한다.
8. 계단 제외 설정이면 30 옵션 결과만 사용한다. 다른 후보의 계단 유무를 추측해서 통과시키지 않는다. 따라서 초기에는 대안이 1개일 수 있다.

**현재 TMAP 후보만으로 ‘강변·공원길 우선’이나 ‘골목 완전 배제’를 보장하지 못한다.** 해당 속성이 있는 실제 보행망·검증된 러닝 코스 연결이 다음 단계다. 출발지와 목적지를 지도 위 자로 연결하는 직선은 경로로 사용하지 않는다.

### 신호와 15초 기준

```text
구간 이동시간(초) = 구간 보행거리(m) / 1000 × 입력 페이스(초/km)
다음 횡단 도착시각 = 실제 출발시각 + 누적 이동시간 + 앞에서 확정된 누적 대기시간
예상 대기 < 15초   → 기준 경로 유지
예상 대기 >= 15초  → 연속성·우회범위를 만족하는 후보만 재비교
```

- `forecast()`는 주기, 기준 epoch, 진입 가능한 녹색 구간, 횡단 완료 여유, 계획 유효기간, 검증시각, 불확실성을 검사한다.
- 점멸/진입 종료 시각 이후에는 다음 진입 가능 구간까지 기다린다. 남은 시간 안에 횡단을 완료할 수 없는 경우도 통과 처리하지 않는다.
- 너비가 없거나 주기가 비정상·계획 만료·검증시각이 오래됨·불확실성이 큰 경우 `null`로 반환한다.
- 앞 신호가 미확정이면 뒤 신호의 도착시각도 확정하지 않는다.
- 신호 없는 경로의 `0초`는 전체 보행 횡단 조사 범위가 완전하다고 입증된 경우만 가능하다.
- `preferSignalRoute()`는 15초 이상일 때만 대안 비교한다. 신호가 없다는 이유로 지그재그나 무제한 우회를 선택하지 않는다.
- 검증시각 60초, 불확실성 3초, 횡단 여유 3초는 시험용 보수적 기본값이다. 제공기관 계획 갱신 정책·현장 검증에 맞춰 재설정해야 한다.
- `server/signal-service.ts`의 `RouteSignalProvider.inspect()`가 실제 신호 연결 지점이다. 기본 구현은 항상 미확인이다. 제공기관 장애가 경로 API 전체를 실패시키지 않도록 되어 있다.
- 서버는 후보별 `forecasts`와 추천 ID를 반환할 준비가 돼 있지만, 실제 화면은 아직 미래 예측을 활성화하지 않는다. 검증된 provider 연결, 같은 후보 필터 적용, 실제 시작시각 재예측을 마친 뒤 화면의 신호 수/대기/다음 횡단 안내를 함께 활성화해야 한다.

예: 6:00/km로 100m 지점에 도착하면 36초가 걸린다. 거기서 24초 기다렸다면 다음 200m 지점 도착은 72초가 아닌 96초다. 테스트에서 이 누적 계산을 검증한다.

## 5. GPS와 기록 계산

| 값 | 계산/정의 |
|---|---|
| 기록 거리 | 유효한 GPS 구간의 누적 거리, WGS84 haversine |
| 운동시간 | running 상태의 경과시간. 실제 신호에서 기다린 시간도 포함 |
| 수동정지시간 | paused 상태의 경과시간 |
| 전체 경과시간 | 운동시간 + 수동정지시간 |
| 운동 평균 페이스 | 운동시간 / 기록거리(km). 화면마다 분모·정지 포함 여부를 일관되게 표시 |
| GPS 정지 추정 | 낮은 관측 속도로 추정한 정지. 신호 대기라고 단정하지 않음 |
| 신호 대기시간 | 검증된 횡단 상태와 정지 구간이 결합돼야 별도 산출 가능. 현재 미확인 |
| 개인 최고 | 같은 방향 경로, 완주 추정, GPS 공백 없음, 순서대로 경로를 따라간 기록끼리 전체 경과시간 비교 |

GPS 오차 30m 초과·역순 타임스탬프·초속 10m 초과 점프를 거리에서 제외한다. 작은 이동은 기준 위치에서 누적해 잡음 제거 때문에 실제 러닝의 모든 3m 이동이 사라지지 않도록 한다. 15초 초과 수신 공백과 수동정지 전후는 선분을 끊는다. 좌표 누락 거리는 직선으로 보간해 달린 것처럼 만들지 않는다.

완주 판정은 경로 시작·종점 근접, 거리 범위, 수신 공백, 순서대로 통과한 경로 샘플을 보수적으로 검사한다. GPS가 나쁘면 실제 완주도 부분 기록으로 남을 수 있다. 운동 자체는 버리지 않고 최고 기록 비교에서 제외한다.

같은 루트는 방향을 유지한 경로 좌표로 묶는다. 장소 이름이 같다는 이유로 다른 경로를 합치지 않는다. 다만 지도 공급자 형상 버전·수 m 좌표 변화가 다른 코스로 나뉠 수 있어, 운영 규모에서는 도로 링크 ID/형상 버전 기반 식별로 전환해야 한다.

## 6. 계정과 저장

`supabase/schema.sql`을 새 프로젝트에 한 번 적용하고 공개 URL/anon key만 프런트 환경변수에 넣는다. service_role 키는 이 프런트에 필요 없고 넣으면 안 된다.

- `profiles`: 자기 프로필만 조회/수정.
- `runs`: 자기 운동 기록만 조회/수정/삭제. UUID 및 소유자 일치 제약.
- `public_routes`: 사용자가 명시적으로 공개한 코스. 공개 조회, 소유자만 수정/삭제.
- `route_likes`: 개인 공감 행은 자기 행만 접근, `(route_id,user_id)` 중복 방지.
- `route_feed`: 고정 SQL 함수로 집계 공감 수와 코스를 최대 20개 반환.
- `delete_my_account`: 로그인한 자신의 계정만 삭제하는 제한된 함수.
- 기기 저장: 별도 IndexedDB `flow-run-real-v1`. 데모 localStorage와 분리.
- 동기화: 자동 외부 전송 대신 사용자가 누르는 계정 동기화 버튼. 로컬 미동기화 UUID upsert 후 계정 기록 수신.
- 다중 기기 동시 제목 수정, 오프라인 삭제 충돌, 대규모 기록 페이지네이션은 별도 운영 개선 대상이다. 현재 삭제는 계정 요청이 성공해야 로컬에서도 제거한다.
- 게스트 기록을 새 계정에 자동 합치지 않는다. 게스트→계정 선택적 이전은 별도 동의 UI와 함께 추가해야 한다.

메일/비밀번호 정책, DB RLS 실제 권한 테스트, 계정 삭제·복구 메일 동작을 실제 프로젝트에서 검증해야 정식 계정을 공개할 수 있다. 현재 정책 화면은 개발 안내이며 사업자/운영자 정보가 확정된 운영용 약관을 대신하지 않는다.

## 7. 실제로 확인해야 할 순서

1. **지도**: 올바른 공개 MapTiler 키와 Origin을 넣고 서울/대구/인천/성남 지도를 연다. 지도 출처 표시는 숨기지 않는다.
2. **장소**: 카카오 REST 키로 대표 장소 검색. 사용자가 선택한 좌표가 실제 장소와 같은지 확인한다.
3. **경로**: TMAP 응답 1개를 저장해 거리·좌표계·경유지·계단제외를 검증한다. 반환점 왕복도 별도 검사한다.
4. **계정**: Supabase SQL/RLS 적용, 이메일 가입/인증/복구/로그아웃/다른 계정의 기록 접근 차단/탈퇴 검사.
5. **GPS**: 야외 1km에서 여러 기종으로 시작·일시정지·재개·수신 공백·화면 잠금·종료·저장·복구 검사. 웹 백그라운드 위치 한계 확인.
6. **서울 1개 교차로**: state/timing/crossroad/connection/lane 실제 응답을 같은 ID로 확보한다. 차량 신호와 보행 신호를 구분한다.
7. **횡단 1개 연결**: 보행 진입점/종점/방향/신호 ID/너비를 현장에서 맞춘다. 교차로 중심 근접만으로 결합하지 않는다.
8. **미래 계획**: 해당 교차로 운영계획·시간대·요일·특수일·예약 변경·옵셋 기준을 확인한다. 현재 상태 반복으로 임의 주기를 만들지 않는다.
9. **예측 비교**: 15초 경계, 점멸, 계획 전환, 오염/지연 응답, 미지원 지역을 실측과 비교한다. 허용 오차와 예측 유효 시간을 정한다.
10. **서비스 확장**: 검증된 횡단/구간부터 지도에 범위를 공개하고, 미지원 구간은 기본 경로로 제공한다. 도시 이름 전체를 지원 범위로 오인시키지 않는다.
11. **정식 배포**: 제공기관 상업 이용/결합/캐시/출처 조건, 실제 운영 정책, 호출량 예산과 모니터링을 확정한다. 앱스토어 배포라면 네이티브 위치·백그라운드 수집/권한 구현과 검증을 별도로 수행한다.

## 8. 이번 변경에서 수정한 기존 코드 문제

- 일반 편도 경로에서 사용자가 선택한 경유지가 `waypoints: []`로 사라지던 문제.
- 왕복 입력을 받으면서 출발=도착이라는 이유로 추천 단계가 실패하던 문제. 명시적 왕복은 경유 구간을 이어 계산한다.
- 대기 15초 미만에도 신호를 이유로 대안을 고르던 문제.
- ‘다른 루트’가 우회 제한·연속성 기준을 통과하지 않은 후보를 보여줄 수 있던 문제.
- `buildReason()` 설명과 사용자 지정 대기 기준이 어긋나는 문제.
- 페이스 계산기의 일반 이벤트 함수를 `usePathDistance`로 이름 지어 Hook 규칙 오류가 나던 문제.

## 9. 검증과 한계

자동 검증은 `npm run build`, `npm run test`, `npm run lint`로 재현한다. 제공기관 응답은 테스트용 fixture이며 실제 키 승인 검증과 구분한다.

테스트 범위: 누적 신호 대기·15초 포함 경계·점멸·만료·미확인 전파·부적합 우회 제외·TMAP 요청 형식·경유지·부분 장애·키 비노출·GPS 잡음·수신 공백·일시정지 시간·완주 판정·중복 기록 저장·계정 분리·가입 서버 미설정·온보딩·페이스 저장 화면.

직접 브라우저 화면 점검은 실행 환경에서 로컬 주소가 차단되어 완료하지 못했다. JSDOM 화면 동작 테스트는 실제 브라우저 지도 렌더링/모바일 레이아웃/GPS 기기 검증의 대체물이 아니다. 지도/Supabase 라이브러리 번들 크기 경고 및 기존 React lint 경고는 추가 개선 대상이다.
